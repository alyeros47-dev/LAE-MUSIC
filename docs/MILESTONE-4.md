# Milestone 4: Flutterwave, Paystack and USD-based local pricing

The owner's selected gateways are **Flutterwave and Paystack**. USD remains the standard product/accounting currency. Country-based currency conversion must not silently change package prices, commission bases, historical balances or the currency actually charged.

## What is connected

The shared navigation now has a display-currency control. It suggests the local currency from the artist's saved country or the browser's explicit region, supports manual country/currency overrides, and remembers the choice in browser storage. A currency change decorates prices without rerouting the page, recreating the player, interrupting playback or discarding form state.

Country defaults are derived from [Unicode CLDR 48](https://github.com/unicode-org/cldr-json/blob/48.0.0/cldr-json/cldr-core/supplemental/currencyData.json) active tender data as of 2026-10-25, with 250 country/territory choices and 153 current tender currency choices. Territories without a mapped official currency use an explicit USD fallback. Multiple-tender territories retain their available choices. This dataset does not establish gateway acceptance. Currency changes and new legal tender require periodic review of the pinned dataset. The Unicode license and source attribution are bundled under `data/`.

Artist packages and generation purchase reviews show the approved USD price plus an approximate selected-currency value. Estimates include the reference timestamp and source attribution. A missing/expired rate displays an unavailable estimate while preserving the USD price. Orders still snapshot their approved USD commercial terms; the selected display currency is never trusted as a payment instruction.

The reference-rate service uses the [ExchangeRate-API open USD feed](https://www.exchangerate-api.com/docs/free), a documented daily reference feed with attribution. The source is fixed in server code; there is no user-supplied URL. Responses have transport timeouts, size limits, base/update validation and rate bounds. Concurrent requests share an in-process refresh; snapshots persist across server restarts. Only current data up to 36 hours old is eligible. Failures are throttled and expired data is not shown as current. The public pricing API returns converted values for the six approved package/generation products, not a redistributable raw exchange-rate feed. Currency coverage depends on the feed; unsupported rates fall back honestly to USD. `FX_RATE_SOURCE=disabled` disables conversion; `exchangerate-api` (the default) selects this reference source. There is no FX markup or newly invented charge.

`005-currency-quotes.sql` adds append-only reference snapshots and immutable local checkout-quote records. Internal quote preparation requires an owned current unpaid order and a currency explicitly approved on the specified merchant account. Quotes expire after five minutes or the order's earlier expiry. A composite database foreign key binds the base amount/currency to the original USD order. Decimal conversion uses integer arithmetic and the currency's fraction digits, including JPY/XOF zero digits and KWD three digits. An FX quote is not a charge, ledger conversion or proof of payment.

## Gateway contracts

The application still does **not** construct a live gateway adapter. Public checkout/webhook endpoints remain unavailable, even if environment keys are added. Adapter factories default to unreviewed, and test success must not be represented as merchant-account verification. No real payment has been received, no live checkout has opened and no payout has been made.

The Paystack adapter follows its [transaction API](https://paystack.com/docs/api/transaction/) and [webhook authentication](https://paystack.com/docs/payments/webhooks/): original bytes are authenticated with HMAC-SHA512 before parsing, then the reference is verified using the secret-key-scoped API. Returned reference and test/live domain must match. The documented response does not provide an independent merchant-ID assertion; account identity is bound through the authenticated secret key and must be confirmed during merchant setup. Checkout includes explicit amount/currency, server-controlled reference and quote/order metadata, with a restricted hosted-checkout domain. Paystack uses its documented multiplier of 100 for XOF even though the currency has no fractional unit; normalization rejects fractional francs. A general country currency must never be mistaken for an enabled Paystack currency. [Paystack currency documentation](https://paystack.com/docs/api/) lists NGN, USD, GHS, ZAR, KES and XOF with country/account restrictions; the adapter additionally requires a configured account allowlist.

The Flutterwave adapter deliberately targets [v3 Standard](https://developer.flutterwave.com/docs/flutterwave-standard-1), [v3 transaction verification](https://developer.flutterwave.com/reference/verify-transaction) and [v3 webhooks](https://developer.flutterwave.com/v3.0.0/docs/webhooks). It checks the v3 `verif-hash` secret in constant time before parsing, then verifies transaction ID/account ID and retrieves status, amount, currency, reference and metadata through the authenticated API. Expected-reference/quote binding still belongs to the future checkout coordinator. Flutterwave v4's `flutterwave-signature` HMAC protocol is a different contract and is not mixed into this v3 adapter. Hosted checkout uses explicit currency and decimal amount, with quote/order metadata and a restricted Flutterwave checkout host. Its charge currencies must be explicitly approved for the actual merchant account; country defaults alone do not enable charging.

Both adapters preserve server references and decline unexpected checkout hosts or malformed amounts. Credentials and original provider payloads are not returned to the browser or logged. Only charge-success/completion event types are normalized; refunds, disputes, settlement statements and payouts still need their own reviewed workflows. No automatic gateway failover or blind checkout retry is implemented: an ambiguous initialization must be reconciled by its reference before creating another attempt.

## Verification and current limits

Local tests pass 89 behavioral/contract cases plus existing Sonic/integrity checks. New coverage includes country defaults, manual override validation, 0/2/3-digit money, rate outage/staleness, concurrent caching, source validation, non-redistribution of rates, signatures, wrong protocol/mode/account, hosted checkout metadata/URLs, XOF units and unapproved currencies. The expanded PostgreSQL journey verifies persisted snapshots, immutable FX quotes and base-price ownership, plus actual Paystack/Flutterwave adapter normalization into the existing transaction service using isolated HTTP-response fixtures. The browser journey changes country/currency while audio is playing and checks converted package prices, attribution and overflow at desktop/tablet/mobile sizes. [CI run 40195582634](https://github.com/alyeros47-dev/LAE-MUSIC/actions/runs/40195582634) passes both jobs: 89 behavioral/contract tests, original integrity/Sonic suites, 32 PostgreSQL tests, socket HTTP checks and desktop/tablet/mobile journeys. A country-selector accessible-label issue found by the first browser run was fixed before the passing run. Current evidence is also recorded in `docs/RELEASE.md`.

These are fixture-backed provider tests, not calls to merchant sandboxes. Workspace network access could not reach its configured HTTP proxy, so a live reference-feed fetch from this application has not been verified here either. No production records or payment credentials were accessed. The actual runtime fetch must be verified in an approved staging environment; unavailable live data falls back to USD.

The existing commerce transaction service accepts verified **USD** payment evidence. A local charge cannot masquerade as USD: it is quarantined without granting a subscription. The local presentment quote structures are preparation for a reviewed checkout coordinator, not an enabled local-currency settlement bridge. Before activation, bind a durable single checkout attempt/reference to its provider and immutable quote; verify provider evidence against the quote's actual charge amount/currency/reference/metadata; then record base USD accounting and original charge evidence separately. Keep separate currency balances and approved FX/fee/settlement treatment. Do not simply rewrite a provider response's currency or multiply a browser-supplied amount.

Still required: the merchant's registered country; approved Flutterwave/Paystack accounts and currencies; separately configured test/live secrets and webhook secret; verified return URLs; sandbox and staging journeys; a durable cross-provider checkout-attempt coordinator; raw-body public webhook ingestion; local-currency settlement/reconciliation and FX/fee/refund/dispute policies; and payout verification. The public gateways must stay closed until these paths are complete and verified. Current NGN gift records and all historical balances are preserved; this milestone does not convert or fund them.
