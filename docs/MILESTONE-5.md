# Milestone 5: Nigeria merchant checkout coordination and local-currency verification

The owner confirmed **Nigeria** as LAE-MUSIC's registered country. `config/payment-merchant.json` records `NG`, USD as the base currency and a disabled checkout mode. Both merchant accounts remain unverified, with empty merchant IDs and approved-currency lists. Country confirmation is not proof of account/KYC or currency approval. The initial charge policy is NGN/USD; the broader country/display-currency converter remains available separately.

## Connected checkout behavior

An owned unpaid purchase can receive a short-lived server quote for a provider/account-approved charge currency. In sandbox mode the artist reviews the provider, exact currency/amount, original USD price and quote expiry before requesting a hosted payment link. The server uses the artist's stored email and its own callback/reference; browser amounts, success flags, merchant IDs and callback URLs are not accepted as payment instructions. The public application keeps checkout closed until the staging runtime requirements below are met.

`payment_checkout_attempts` durably binds one order to one quote, provider, merchant, mode and random reference before an external initialization request is sent. Database uniqueness and creator/order locks prevent simultaneous tabs or competing providers from starting two checkouts for the same purchase. A repeated request returns the existing attempt. A different provider/currency cannot bypass the existing reference. The current coordinator keeps one attempt per order permanently; there is no reset/release endpoint yet. Definitive cancellation, retry/recovery and refund rules must be completed before live operation. Purchase cancellation is blocked once initialization has started, so it cannot race payment acceptance.

Provider initialization happens outside the database transaction. A timeout, rejected/unreadable response, missing response reference or failure saving the URL retains the attempt for reconciliation. The service does not blindly repeat the POST, fail over to another gateway or claim that no payment was accepted. A process interrupted after reservation also keeps its durable reference across workers. A webhook arriving before the URL response can verify the purchase; a late initialization response cannot overwrite that verified state. Hosted URLs are restricted to approved provider domains and only shown while the quote is current.

The artist can check the reference through the same authenticated purchase screen. This performs an independent provider lookup by the stored reference, without synthesizing a provider webhook or asking for another charge. A durable 15-second lookup interval prevents rapid repeated owner requests from flooding the provider, including across workers. Only owned references are visible. The administrator can review checkout states, failure codes, base values and original charge currencies in the protected Checkouts report. There is no manual mark-paid or cash-credit operation.

## Verification and accounting boundary

The provider-specific webhook routes authenticate the original bounded request bytes before using the payload. Only exact POST paths `/api/platform/payments/webhooks/paystack` and `/api/platform/payments/webhooks/flutterwave` bypass browser-origin checks; both still require provider authentication. Other mutations retain normal origin and account protections. Bodies have content-type, length and idle-time limits. Existing aggregate/unconfigured payment endpoints remain unavailable.

After webhook authentication or an owner-authorized lookup, the service independently retrieves payment data and matches transaction/reference, merchant, test mode, order metadata, immutable quote ID, exact charge amount and charge currency. It also checks the purchase/quote expiry. Client redirects and success flags cannot fulfill an order. Unknown, mismatched or delayed payments go to append-only review evidence without granting access. A paid quote replay can be recognized after expiry without creating another receipt. Payments received after quote/order expiry are deliberately quarantined; a verified provider refund/review workflow is still required before live operation.

A valid NGN payment is compared against the NGN quote, not relabeled as USD. The USD order amount remains the commercial/accounting base. `payment_presentments` preserves original charge amount/currency, provider/merchant/payment ID, reference, quote/attempt and mode. Base and original-charge foreign keys bind it to the order/quote. The USD receipt, journal, subscription or studio-credit entitlement, approved pending commission, original-charge evidence, attempt state and audit event commit together. Any persistence failure rolls them all back. Multiple events/retries cannot create multiple entitlements or sale journals.

The base USD receivable is a quote-based book value, not proof of a USD bank deposit. Original NGN charge evidence remains separately auditable. No provider fee, FX gain/loss, settlement cash, historical balance conversion or commission clearance is invented. Artists cannot withdraw pending commissions or provider receivables. Confirmed bank settlement, fees/FX reconciliation, funded royalties, refunds/disputes and bank payouts remain separate outstanding work. Existing package prices, approved commissions, royalties and the 3% withdrawal fee are preserved. Extra-generation purchases grant one generation without an invented affiliate rate.

Webhook evidence is labeled `webhook`; independent server reconciliation is labeled `server_lookup`. Both keep a hash and whitelisted verification details, not signing secrets, raw card data or full provider payloads. A lookup records what the provider actually returned; it does not fabricate a successful webhook.

## Safe runtime setup

`lib/payments/runtime.js` connects the coordinator to the existing platform handler. No generic environment toggle or merely adding credentials activates it. The versioned merchant manifest must explicitly specify sandbox mode and reviewed merchant IDs/currencies, the service must run as `NODE_ENV=staging`, the keys must be test keys, and a valid HTTPS staging callback origin must be provided. The known production origin is rejected. The standard server remains disabled with the committed manifest; `live` mode is not supported by this candidate.

Only after an independently approved staging environment exists:

1. Keep its database/bucket isolated from production. Back up and validate migrations on a sanitized production-schema clone first. Apply `006-checkout-attempts.sql` through the existing checksummed migration runner; do not edit migrations 001–005 or discard conflicting records.
2. Verify each real merchant test account and its approved NGN/USD charge currencies. In a reviewed manifest change, set the actual test merchant IDs, approved currency lists and account review state. Set `checkout_mode` to `sandbox` only for that staging candidate. This review is not established by this repository's mocked tests.
3. Set `NODE_ENV=staging`, `PAYMENT_CALLBACK_ORIGIN`, `PAYSTACK_SECRET_KEY`, `FLUTTERWAVE_SECRET_KEY` and `FLUTTERWAVE_WEBHOOK_HASH` through the staging secret manager. Never paste keys into chat or commit them. The Flutterwave v3 hash must be a long random secret. Current source intentionally uses v3 `verif-hash`, not v4 HMAC headers.
4. Register the two exact HTTPS webhook URLs in the corresponding provider test dashboards. Exercise hosted checkout, returning to the owned status screen, original-byte authentication, independent lookup, exact NGN/USD quote matching, duplicate/concurrent events, expiry, uncertain acceptance and service restart.
5. Keep production mode disabled. Live activation requires real sandbox evidence, reviewed refunds/disputes and cancellation/recovery operations, settlement/fee/FX accounting, operational monitoring, security review and explicit production deployment approval.

The first provider currency facts are documented in [Paystack's currency API](https://paystack.com/docs/api/). Flutterwave reference reconciliation follows its [v3 reference verification API](https://developer.flutterwave.com/reference/verify-transaction-with-tx_ref); successful payments are always independently verified before value is given, as described in [Flutterwave verification guidance](https://developer.flutterwave.com/docs/transaction-verification). Repository policy still requires exact amounts and quarantines overpayments; it does not silently grant value and invent a refund.

The feature is ready for code review and controlled staging verification, not commercial launch.
